## Detailed Architecture And Design

This section records how the Layer 6A system is connected at the current point in the implementation. The core design rule is unchanged: product UI code talks to the repo-owned `vacuum_adapter` contract, never directly to TurtleBot4/Nav2, Valetudo, ROS topics, Valetudo HTTP, Valetudo MQTT, or robot-vendor capability names.

### High-Level Product Architecture

```text
VS Code extension
  -> webview bootstrap/config injection
  -> panels-standalone VacuumControlPanel
  -> useVacuumAdapter
     -> TurtleBot4/Nav2 backend adapter
        -> tensorfleet-ros / ros2Bridge
        -> vm-manager ROS/Foxglove proxy
        -> VM TurtleBot4/Nav2 simulation runtime
        -> Gazebo/TurtleBot4/Nav2 services, topics, and mission services

     -> Valetudo backend adapter
        -> Valetudo runtime client
        -> vm-manager Tensorfleet-Mgr proxy
        -> VM-managed Valetudo integration runtime
        -> Valetudo mock HTTP source or optional MQTT source cache
        -> real Valetudo-compatible vacuum later
```

The product-facing shape is therefore:

```text
UI intent and rendering
  -> VacuumAdapterSnapshot + VacuumCommand + VacuumCommandResult
  -> backend-specific adapter hook
  -> backend-specific runtime boundary
  -> backend runtime/source
```

The current Layer 6A Valetudo proof path is:

```text
Valetudo mock-shaped HTTP data
  -> tensorfleet-mgr Valetudo integration runtime
  -> /api/v1/valetudo/health
  -> /api/v1/valetudo/snapshot
  -> /api/v1/valetudo/command
  -> Valetudo runtime client in panels-standalone
  -> Valetudo backend state/command mappers
  -> vacuum_adapter snapshot and command result
  -> existing VacuumControlPanel UI
```

### Vacuum Adapter Boundary

The public adapter surface is intentionally small:

```ts
type VacuumAdapter = {
  snapshot: VacuumAdapterSnapshot;
  sendCommand: (command: VacuumCommand) => Promise<VacuumCommandResult>;
};
```

The snapshot is the single normalized read model for the panel. It includes:

- `identity`: backend-neutral identity with `source` set to `turtlebot4_nav2`, `valetudo`, or `mock`.
- `availability`: online/offline/connecting state.
- `capabilities`: normalized feature and command flags.
- `map`: grid, metadata, annotations, and map readiness.
- `pose`: backend-neutral pose readiness and coordinates.
- `navigation`: go-to/navigation lifecycle state.
- `mission`: legacy coarse mission state used by older UI paths.
- `activeMission` and `missions`: normalized active/recent mission snapshots.
- `mapping`: mapping session state and saved-map summaries.
- `readiness`: product-level "can operate" summary.
- `fault`: normalized fault/degraded state.
- `battery`: battery percentage and charging state.

The command surface is also backend-neutral. It includes current TurtleBot4/Nav2 commands plus Layer 6A vacuum commands:

```text
start_cleaning
pause
pause_mission
stop
cancel_mission
return_to_dock
```

Other command names exist in the contract for future or TurtleBot4-backed workflows, including navigation, mapping, coverage, rooms, zones, fan speed, and water usage. The Valetudo adapter currently returns explicit unsupported results for those unless the implementation is product-ready.

### Backend Selection In The UI

`useVacuumAdapter` selects exactly one backend hook for a component instance:

```text
VacuumControlPanel
  -> state backend = readConfiguredVacuumAdapterBackend()
  -> VacuumControlPanelContent key={backend}
  -> useVacuumAdapter({ backend })
     -> if backend === "valetudo": useValetudoAdapter()
     -> otherwise: useTurtleBot4Nav2Adapter()
```

The `key={backend}` remount is important because React hooks cannot switch which hook tree they call during the lifetime of a mounted component. The backend is pinned in a ref inside `useVacuumAdapter`, so each mounted panel instance has one stable backend path.

### Valetudo Source Modes

The runtime currently supports two source modes:

```text
VALETUDO_RUNTIME_SOURCE_MODE=valetudo_mock  # default
VALETUDO_RUNTIME_SOURCE_MODE=fixed_mock     # internal deterministic regression mode
```

Default HTTP mock-source mode:

```text
tensorfleet-mgr
  -> GET /api/v2/robot
  -> GET /api/v2/robot/state/attributes
  -> GET /api/v2/robot/capabilities
  -> PUT /api/v2/robot/capabilities/BasicControlCapability
```

The default source base URL is:

```text
http://172.16.0.1:8081
```

That address is the host-side Firecracker TAP address from the VM's point of view. It can be overridden with:

```text
VALETUDO_MOCK_SOURCE_URL
VALETUDO_SOURCE_URL
VALETUDO_SOURCE_TIMEOUT_MS
```

Fixed mock mode keeps an internal deterministic state machine inside `tensorfleet-mgr`. It can simulate reachability and BasicControl availability with:

```text

VALETUDO_FIXED_MOCK_BASIC_CONTROL_AVAILABLE
```

- Unsupported Valetudo product surfaces still produce complete, non-crashing snapshot fields.

### State Mapping

The VM runtime normalizes Valetudo source state into:

```text
state.value
state.label
state.started
state.paused
```

The extension-side mapper then converts runtime state into the public mission model:

| Runtime state signal | Public mission state |
| --- | --- |
| `state.paused` or state value containing `pause` | `paused` |
| state value containing `return` | `returning` |
| `state.started` or state value containing `clean` | `cleaning` |
| `battery.charging === true` | `charging` |
| otherwise | `idle` |

If the mapped mission state is not `idle`, `stateMapper.ts` creates a lightweight `activeMission` with type `hardware_cleaning` or `return_to_dock`. This gives the existing mission UI something backend-neutral to render without pretending that Valetudo has Nav2 waypoints, coverage progress, or map-grid progress.

### Failure And Stale-State Behavior

There are two different failure zones:

```text
Extension cannot reach runtime
  -> useValetudoAdapter catches fetch/shape errors
  -> maps to offline adapter snapshot
  -> UI stays mounted

Runtime can run but cannot reach Valetudo source
  -> /health reports source.status = unreachable and source.stale = true
  -> /snapshot returns stable top-level runtime shape with unavailable source state
  -> /command returns structured unavailable result
```

This distinction matters because the product UI should not crash in either case:

- Runtime transport failure means the adapter cannot get any valid runtime snapshot.
- Source failure means the runtime itself is healthy enough to report that the Valetudo source is stale or unreachable.

Known current normalization gaps to track:

- In the current runtime code, unreachable HTTP mock-source snapshots can report command unavailability as `capability_unavailable` instead of `source_unreachable` because capability presence is checked before reachability.
- In the current runtime code, HTTP-source dock state is derived from robot status and does not yet preserve Valetudo `DockStatusStateAttribute` values such as `emptying`, `cleaning`, or `drying`.

### Runtime API Boundary Versus Valetudo Source Boundary

The runtime API is backend-neutral enough for the extension adapter:

```text
/api/v1/valetudo/health
/api/v1/valetudo/snapshot
/api/v1/valetudo/command
```

The Valetudo source API remains private to the VM runtime:

```text
/api/v2/robot
/api/v2/robot/state/attributes
/api/v2/robot/capabilities
/api/v2/robot/capabilities/BasicControlCapability
```

The extension-side Valetudo adapter must not call the source API. This keeps the later real-hardware or MQTT path free to change inside the VM runtime while preserving the product-facing `vacuum_adapter` contract.

### Current Out-Of-Scope Boundaries

These are intentionally not connected yet:

- Real Valetudo-compatible robot hardware.
- Valetudo MQTT production hardening.
- Valetudo map rendering in the product UI.
- Valetudo pose as a product navigation surface.
- Valetudo go-to execution.
- Segment, room, zone, and clean-area execution through Valetudo.
- Fan speed and water usage setters.
- Consumables UI polish.
- Runtime-owned Valetudo mission history.
- Scheduling, fleet management, and cloud deployment strategy.
- Any rewrite of the existing Vacuum Control panel to be Valetudo-specific.

### Why This Design Fits The Immediate Goal

The immediate goal is not to build every Valetudo feature. It is to prove that Valetudo-shaped state, capabilities, and basic commands can travel through the same product-facing adapter boundary used by the existing UI.

The implemented architecture proves that by keeping these boundaries stable:

```text
Valetudo-shaped source data
  -> normalized runtime API
  -> Valetudo backend adapter
  -> vacuum_adapter
  -> existing UI
```

The TurtleBot4/Nav2 path stays valuable because it remains the simulation/regression backend:

```text
existing UI
  -> vacuum_adapter
  -> TurtleBot4/Nav2 adapter
  -> ROS2/Nav2/Gazebo runtime
```

The Valetudo path can therefore grow feature by feature behind the adapter without making product UI code depend on Valetudo internals.
